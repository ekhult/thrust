Get inside

Stages 1–3
01

Read the floppy disk

The game came as a .d64 file, a byte-for-byte copy of a C64 floppy. A small reader walked its 35 tracks, found the directory and pulled out the game program.

The program was a cracked release, so it was not the game itself but a compressed bundle that unpacks the game when run.

02

Unpack it by letting it unpack itself

Instead of decoding three different packers by hand, the packed program was run inside an emulator. Each layer decompressed the next. The emulator stopped when execution reached $6C24, the real start of the game, and saved all 64 KB of memory.

That memory dump is the game exactly as it sits in a C64 the moment it starts.

03

Build a C64 in software

To watch the game work, a small C64 was written in Python: a 6502 processor plus just enough of the other chips for Thrust to run. Pressing keys and taking screenshots could then be scripted, and memory could be changed between frames.

It runs about 300 frames a second, so experiments that take minutes on a real C64 finish in seconds.

Understand

Stages 4–6
04

Map the code

The memory was turned back into readable 6502 assembly. A tracer logged every subroutine the game called while being played, which showed which bytes were code and which were data. From there the main loop at $B1AD was found and each of its 20 calls was given a meaning.

Variables were named one by one: ship position in $07–$0C, angle in $0D, level in $A4.

05

Pull out the data

Each planet is stored as two packed streams of numbers: where the left wall and the right wall are on every row. Decoding them redrew all six planets. Object tables gave every gun, fuel cell, reactor and pod. Sprites, the font, colours, doors and restart points came out the same way.

Every map was checked by running the game's own drawing code in the emulator and comparing.

06

Recover the physics and rules

The flight code was rewritten in Python and run side by side with the original on random input. Every difference was traced back to the assembly until the two matched bit for bit over 3,000+ game ticks, with and without the pod.

Rules were tested the same way: injected bullets confirmed the scores (150, 750), and a score of 9,990 + 750 confirmed the extra ship at 10,000.

Rebuild

Stage 7
07

Write the Mac game

The game was rebuilt in Swift as a native macOS app. Game logic, physics and level data follow what stages 4–6 found. It draws into a 320×200 picture in the C64 palette, just like the original screen, then scales it up and smooths movement between the 32.55 Hz ticks.

The sound is not rewritten at all: Rob Hubbard's music player and the effects driver are the original 6502 code, run on a tiny 6502 inside the app.

Prove and ship

Stages 8–9
08

Test the port against the original

The C64 detects crashes in its graphics chip, when ship pixels touch rock pixels. That chip feature was added to the emulator, then the ship was placed at 1,624 positions on all six planets, in both games, and each was asked: crash or not?

This found one real bug: sprites sat one screen line too high, because the C64 starts drawing a sprite one line below its Y value. Earlier, a play-through past planet 6 found a pod that failed to reappear. Both are fixed.

09

Package it

A build script compiles one app for both Apple Silicon and Intel Macs. A second script wraps it in a standard installer that puts Thrust in the Applications folder.

The installer is not signed with an Apple developer ID, so macOS asks for permission the first time it is opened.
